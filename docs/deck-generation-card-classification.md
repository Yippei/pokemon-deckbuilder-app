# デッキ生成用カード仕分け案

更新日: 2026-07-18

この文書は、AIデッキ生成の候補カードをカードマスターから安定して抽出するための初期仕分け案です。  
まだ実装ルールではなく、レビュー用の設計メモです。

## 目的

- AIに存在しないカードや古いカード知識を使わせない
- メインポケモン、タイプ、方針、補足指定に合う候補だけを渡す
- 毎回同じ汎用カードだけに寄る状態を避ける
- エネルギー過多、進化元不足、専用テーマカード混入を防ぐ
- 生成ごとに前回デッキの影響を受けないようにする

前提: 現在のカードマスター内のカードは、すべてスタンダードレギュレーション対象として扱います。  
そのため、生成候補抽出では `regulation` の値による除外は行いません。

## 今まで起きた問題と仕分けで防ぐこと

| 問題 | 仕分け側の対策 |
| --- | --- |
| ニンフィアexなのにイーブイが入らない | `evolution_family` で進化ラインをコード側で確定する |
| 補足指定カードが無視される | `requested_cards` を最優先の保護枠にする |
| カスミのコダックのような専用カードが混入する | `character_theme_locked` を作り、テーマ一致時のみ許可する |
| トウコのような汎用サポートまで弾きそうになる | 人名カードを一律禁止せず、効果テキストと対象ポケモンで分類する |
| リブートポッドなどACE SPECが固定化する | `ace_spec_candidates` からデッキ特徴に応じて1枚だけ選ぶ |
| 生成のたびに前回構築を引っ張る | `existingDeck` を候補抽出とAIプロンプトに渡さない |
| 闘デッキに悪エネルギーが過多になる | 選択タイプ外ポケモンのワザ要求を基本エネルギー計算から除外する |
| エネルギー15枚以上になる | `energy_budget` で上限をコード側で強制する |
| 同名カードが別枠で出る | `nameNormalized` 単位で枚数を合算する |

## 仕分けインデックス案

生成時に使う索引は、以下のJSON群または1つの統合JSONとして作る想定です。

```text
pokemon_by_name
pokemon_by_type
pokemon_by_stage
pokemon_by_evolution_family
pokemon_with_ability
pokemon_by_attack_energy

trainer_by_role
energy_by_type
special_energy_by_type
ace_spec

character_theme_locked_cards
generic_staples
deck_plan_cards
```

## ポケモン分類

### `pokemon_by_name`

メインポケモン名から候補を探すための索引です。

用途:
- ユーザー指定の中心ポケモンを確定する
- 同名カードの別バージョンを候補配列として保持する
- 特性、ワザ、HP、タイプで最適なバージョンを選ぶ

### `pokemon_by_evolution_family`

進化ラインを崩さないための索引です。

使用属性:
- `familyId`
- `evolvesFrom`
- `stageCategory`
- `stageOrder`

ルール:
- 進化ポケモンが入る場合、対応する進化前を必ず候補に入れる
- 2進化の場合、原則たねは必須
- 1進化を飛ばすカードがある場合のみ中間進化を薄くできる
- メインポケモンが進化ポケモンなら、進化元は保護枠にする

### `pokemon_by_type`

選択タイプに合うポケモン候補を作る索引です。

現時点のポケモンタイプ件数:

| タイプ | 件数 |
| --- | ---: |
| 草 | 415 |
| 炎 | 299 |
| 水 | 361 |
| 雷 | 256 |
| 超 | 408 |
| 闘 | 336 |
| 悪 | 323 |
| 鋼 | 206 |
| ドラゴン | 106 |
| 無 | 350 |

ルール:
- タイプ指定がある場合、基本は同タイプを優先する
- 別タイプポケモンは、特性や役割が明確に噛み合う場合だけ許可する
- 別タイプポケモンを入れても、基本エネルギー配分はメインタイプを優先する

### `pokemon_with_ability`

システムポケモン候補です。

現時点の単純集計:
- 特性持ちポケモン: 703件

注意:
- 特性持ちなら何でも良いわけではない
- 専用テーマ特性、タイプ専用特性、進化ライン依存特性を分ける必要がある

| --- | --- |
| 草 | グロウ草エネルギー |

## タイプ専用カード分類

### `type_specific_cards`

カード名または効果テキストに以下が含まれるカードを候補にします。

```text
{タイプ}エネルギー
{タイプ}ポケモン
{タイプ}タイプ
```

現時点のトレーナーズ/エネルギー側の初期判定:
- 8件

これは主にタイプ専用特殊エネルギーです。  
今後マスターにタイプ指定トレーナーズが増えた場合は、自動で候補化できます。

## 専用テーマカード分類

### `character_theme_locked_cards`

「カスミのコダック」のように、カード名や効果が特定キャラクター/専用ポケモン前提のカードです。

ルール:
- メインポケモン、補足、方針に該当テーマがある場合だけ許可する
- 汎用サポートの人名カードは一律禁止しない
- 判定はカード名だけでなく、効果対象も見る

例:
- `カスミのコダック`: カスミ軸でのみ許可
- `ヒビキの冒険`: ヒビキのポケモン軸でのみ許可
- `トウコ`: 汎用カードとして別判定

## 方針別分類

### `deck_plan_cards`

ユーザーが選ぶ方針を、候補カードの重みに反映します。

```text
安定型:
  pokemon_search, draw, hand_refresh を高評価

速攻:
  pokemon_search, energy_acceleration, switch を高評価

手札干渉:
  hand_refresh, opponent_hand_disruption, gust を高評価

LO:
  disruption, recovery, defensive_stadium を高評価

耐久:
  heal, recovery, tool, defensive_stadium を高評価

コンボ:
  search, draw, topdeck_setup, recursion を高評価
```

## 生成時の候補抽出フロー案

```text
1. 入力を正規化
   - selectedType
   - mainPokemonName
   - selectedPlan
   - supplementalTheme

2. メインポケモン候補を確定
   - pokemon_by_name から候補配列を取得
   - 特性、ワザ、タイプ、進化段階でスコアリング

3. 進化ラインを確定
   - pokemon_by_evolution_family から進化元を保護枠へ入れる

4. タイプ候補を追加
   - pokemon_by_type
   - energy_by_type
   - special_energy_by_type
   - type_specific_cards

5. 方針候補を追加
   - deck_plan_cards
   - trainer_by_role

6. 汎用カードを追加
   - generic_staples
   - ただし固定採用ではなく、足りない役割を埋める候補として扱う

7. 専用テーマカードを除外
   - character_theme_locked_cards をテーマ一致時だけ許可

8. AIへ候補カードだけ渡す
   - 候補外カードは使わせない

9. 生成後にコード検証
   - 60枚
   - 同名4枚
   - ACE SPEC 1枚
   - 進化ライン
   - エネルギー上限
   - メインタイプ整合
```

## 決定事項

- タイプ専用特殊エネルギーは、各タイプの生成候補に入れる
- エネルギー上限は、まず「原則11枚、例外12枚、13枚以上は補正」で進める
- 別タイプのシステムポケモンは、ゲーム進行を明確にスムーズにできる場合は許可する
- 人名カードの専用/汎用判定は、最初は手動補正リスト方式で進める
- 生成候補は「候補外禁止」にする

## 別タイプシステムポケモンの扱い

別タイプポケモンは原則採用しません。  
ただし、アタッカーではなく特性によってゲーム進行を補助するカードは、システムポケモンとして例外的に許可します。

例:
- `キチキギスex`
  - アタッカー目的ではなく、特性による手札補助・ゲーム進行補助として評価する
  - どのタイプのデッキにも入る可能性があるシステムポケモン候補として扱う

ルール:
- 別タイプシステムポケモンは、基本エネルギー配分の主因にしない
- 選択タイプ外のワザ要求エネルギーは、原則として基本エネルギー枚数の計算から除外する
- 採用枚数は基本1枚、多くても2枚までを目安にする
- 専用テーマや特定ポケモン前提の特性は、テーマ一致時のみ許可する

## 候補外禁止の扱い

AIには候補カードのみを渡し、候補外カードは使わせません。  
候補外カードが出力された場合は、生成後の検証で削除し、候補内のカードで補完します。

この方針により、以下を強く防ぎます。

- 存在しないカードの混入
- 古い知識によるスタンダード外カードの混入
- 前回生成で使ったカードの固定化
- テーマ専用カードの誤採用
- タイプ外カードの過剰採用

## 次の実装候補

1. `front/public/card-generation-index.json` を生成するスクリプトを作る
2. `front/lib/api.ts` の候補補正処理でこの索引を読む
3. Lambdaの `buildCandidateCardPool` に同じ仕分けロジックを反映する
4. 代表ケースのテストを作る

代表ケース:
- ニンフィアex -> イーブイ必須
- 闘タイプ -> 悪エネルギー過多禁止
- リザードンex -> ヒトカゲ/リザードを確保
- ヒビキ指定なし -> ヒビキ専用カード禁止
- 補足でネオアッパーエネルギー指定 -> ACE SPEC枠として優先
